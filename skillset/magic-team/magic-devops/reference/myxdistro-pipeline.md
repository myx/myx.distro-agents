# myx.distro-* pipeline and console family

Read this when working on `myx.distro-*` itself (source/deploy/system/remote/.local packages), a workspace's console entry points, or fleet-execution tooling (`ExecuteParallel`/`ExecuteSequence`/`ShellTo`).

## A different, larger system — don't conflate with myx.common

`myx.distro-*` (`myx.distro-source`, `myx.distro-deploy`, `myx.distro-system`, `myx.distro-remote`, `myx.distro-.local`) is a project build/deploy pipeline, not a simple CLI dispatcher — treat as genuinely separate terrain from myx.common. Its source-level vocabulary (pipeline stages, `project.inf`, context env vars, declarative directives) is the owning `keeper-*`'s territory now — see that skill for the details. This file covers *operating* the pipeline: consoles, fleet execution, and real build/deploy runs against real infra.

## `builders/` is an overloaded directory name — establish the convention before reasoning

Three unrelated conventions share the directory name `builders`. Anything reasoning about "builders" establishes which one it is looking at before drawing a conclusion: a stage-name filter applied to an infra tree matches nothing, and an instance-name directory is not a stage.

- **Per-stage — the distro packages, and any project declaring its own.** `builders/<stage>/<NNNN>-*.sh`. This is the pipeline sense, and the only one the stage vocabulary below describes.
- **Per-instance — infra trees.** `infra/instances-*/builders/<instance-name>`, one directory per provisioned host, each carrying its own `project.inf`. No stage-named directory exists at that level at all.
- **Dynamic provisioning — under a service tree.** A `builders/` directory holding VM launch and destroy scripts, paired per target rather than numbered per stage.

## The full stage vocabulary — what is callable, and what was only ever planned

The keeper owns each stage's source-level semantics; recorded here is the operator-facing half — which stage names are callable and which are not. The designed stage list is longer than the pipeline that exists. It survives only as a design sketch in `myx.distro-source/readme.txt`, between the `----------------` markers, and most of its entries have no code behind them. Mistaking that sketch for an interface means invoking stages that do not exist, so every name below carries a status established by searching the tree.

**Six stages are callable.** They are exactly the set `AllBuilders.fn.sh`'s stage filter accepts (`myx.distro-system/sh-scripts/AllBuilders.fn.sh`) — the same six `myx.distro-source/sh-lib/help/HelpSelectStage.include` documents and `myx.distro-source/README.md` tabulates. The stage set is what the filter enumerates; the builders inside a stage are open-ended. Any project, in any workspace, may declare its own `builders/<stage>/<NNNN>-*.sh` and it is discovered and run — the directories currently in this tree are what this tree happens to carry, not the definition of anything.

Counts below are **builders on disk**, not mentions of the name. A mention count runs an order of magnitude higher and says nothing about whether a stage does anything — `source-publish` is named in 7 files and has no builders at all.

- `source-prepare` — builders `1???-*`. 6 builders. Runner `BuildCachedFromSource.fn.sh`.
- `source-process` — builders `2???-*`. 14 builders. Runner `BuildOutputFromCached.fn.sh`.
- `source-publish` — builders `3???-*`. **0 builders and no runner.** No `builders/source-publish/` directory exists anywhere in the tree, and no `AllBuilders --executables source-publish` call exists anywhere either — so nothing would execute the stage even if builders were added to it. It shares the `3???` range with `image-prepare` deliberately, for the reason given under "`export/` and `distro/` are two different trees" below. Two consequences, and only one of them is real at execution time: **ordering is unaffected**, because a stage selection compiles to `grep '/builders/<stage>/'` and a runner therefore sees only its own stage's builders, in their own order; **discovery collides on basename**, because `ScanSourceBuilders.include` keys its result map on the builder basename alone across every project and every stage, so two builders sharing a basename collapse to one and the loser is never listed.
- `image-prepare` — builders `3???-*`. 5 builders. Runner `BuildDistroFromSource.fn.sh`.
- `image-process` — builders `4???-*`. 2 builders, **both echo-only markers** — `4011-deploy-init.sh` and `4911-deploy-apply.sh`, a started/finished pair that prints and does nothing else. No runner.
- `image-install` — builders `5???-*`. 2 builders, **both echo-only markers** — `5011-deploy-init.sh`, `5911-deploy-apply.sh`. No runner.

**A stage is a runner, not a filter token plus a directory.** The runners are `myx.distro-source/sh-scripts/Build*.fn.sh`, and all three share one four-part shape: ingest the previous tier, export the env-path contract, run that one stage's builders in sorted order, publish the index. `BuildDistroFromSource.fn.sh` shows it whole — `DistroImagePrepare --ingest-distro-image-from-output`, then `export` of `MDSC_SOURCE`/`MDSC_CACHED`/`MDSC_OUTPUT`/`OUTPUT_PATH`/`DISTRO_PATH`/`EXPORT_PATH`, then a loop over `Distro AllBuilders --executables image-prepare`, then `DistroImagePrepare --ingest-distro-index-from-processed`. Those variables are rebound per stage and are the contract builders read: `image-prepare/3000-env-from-output.sh` hard-asserts each one against its expected path and `return 1`s the whole stage on a mismatch, an unset `EXPORT_PATH` included. Three of the six stages have a runner; three do not, which is what makes a stage selectable but inert rather than merely empty.

**What "publish" currently means, concretely.** `image-prepare/3899-distro-ready.sh`, that stage's last builder, logs `distro-ready: publishing distro and export.` and `rsync -ai --delete`s `.local/output-cache/distro/` to `$MMDAPP/distro` and `.local/output-cache/export/` to `$MMDAPP/export`, the two in parallel. Both targets are local paths in the same workspace. Nothing in the pipeline carries either tree off the machine.

**Nine names are planned only — never call these.** Zero files mention any of them as a stage: `image-publish`, `image-receive`, `image-upgrade`, `deploy-prepare`, `deploy-settings`, `deploy-reinstall`, `deploy-actions`, `execute-remote`, `monitor-checks`. (`deploy-settings`'s only textual hits are local, unpublished sketch notes naming an unrelated ndci hook script; a `DeploySettings.fn.sh` tool does exist, and a tool is not a pipeline stage.)

**The Java tree holds none of the model.** `myx.distro-system/java/ru/myx/distro/` speaks an older, different vocabulary — `--build-distro-from-sources`, `--import-from-cached`, `--clean-cached`, `--make-packages-from-folders`. `builders/AbstractBuilder.java` declares `enum BuildStage { DONE_CLEAN_TEMP, // }`: one value and an empty comment. The intent to enumerate stages is visible; the content never existed. Do not go looking there for it.

### `stage:submode` is the mechanism already in production

Stages are not the only unit of the vocabulary, and are not the busiest one. A stage name followed by a colon and a submode is a tag a project declares in its own `project.inf` `Provides:`/`Declares:`, which a builder of that stage then selects on via `ListDistroProvides --select-changed --filter-and-cut "<tag>"`. Declared-tag counts in real `project.inf` files: `image-install:context-variable` 12, `image-prepare:context-variable` 8, `image-prepare:sync-source-files` 6, `image-install:exec-update-before:host` 6 (two levels of nesting), `deploy-export:sh-scripts` 6, plus `image-prepare:clone-source-file`, `image-*:target-patch-script`, `image-install:deploy-sync-files` and roughly fifteen more.

Two sketch entries are submodes rather than stages:

- `deploy-export` — implemented, and the one planned-looking name whose status differs from its neighbours: mentioned in 12 files, and in production as `deploy-export:<path>` tags across all four `os-myx.common*` packages, consumed by the builders `source-process/2801-copy-exports.sh` and `image-prepare/3895-sync-export.sh` — both of which sit in stages that have a runner. What those two builders each produce, and why they differ, is "`export/` and `distro/` are two different trees" below.
- `source-prepare:increment` — a submode of `source-prepare` with a working builder and no declarer. `builders/source-prepare/1201-increment.sh` selects on the tag and writes `source/<project>/build.number`, but no project declares the tag yet, so nothing selects.

### The data flow the sketch encodes

Three artifact tiers, and the stage owning each transition:

- `source` — the checked-out project sources; `source-prepare` collects and caches them, producing no further tier.
- `source` → `cached` — `source-process`.
- `source` + `cached` → `distro` — `image-prepare`.
- `distro` — the deploy-ready output. `image-process` shares repositories from it; `image-install` runs the deploy tasks off it.

`image-receive` is the planned counterpart to that entire left-hand side: pull a `distro` without holding any source. It has no implementation, so building from source is the only way to obtain a `distro`.

The implemented pipeline names one tier more than the sketch does — `README.md`'s stage table reads `source` → `cached` → `output` → `distro`, with `source-prepare` writing `cached`, `source-process` writing `output`, and `image-prepare` writing `distro`. The two vocabularies are not interchangeable; the README is what the code does.

### `export/` and `distro/` are two different trees

One `deploy-export:<local-path>:<public-url-path>` declaration lands in two shapes, at two tiers:

- `builders/source-process/2801-copy-exports.sh` places the content at `$MDSC_OUTPUT/distro/<project>/<src>` — one location, organised per project.
- `builders/image-prepare/3895-sync-export.sh` places it at `.local/output-cache/export/<external-url-path>` — organised by the external address itself, so the export tree mirrors the layout of the public URLs the declarations name.

What each tree is:

- `distro/` is a single location holding prepared files. It is not external repos or places.
- `export/` holds prepared export locations, each of which should have its own actual publish command. Git is one such command, not the only one.

**This is why publish and prepare share the `3???` range.** A deploy-only machine pulls those targets into its own `export/` during `image-prepare`; a source machine publishes out. One position in the lifecycle, opposite directions depending on the machine's role.

**The per-target publish commands are not implemented.** Nothing carries a prepared export target to the location its prefix names, and no mechanism selects a publish command by target type. How that mechanism should work is an open question, held as a blocked board item pending a decision. On a machine carrying both source and deploy, the `export/` folder source produces is already exactly what a pure deploy machine would pull, so deploy uses it directly — which is why publish has never been finished: the combined case never needs it.

### Three open design questions

The sketch marks three stages with a `?` against a submode alternative. All three are open questions, recorded here as questions:

- `source-publish` as its own stage, versus a `publish` submode of `source-process` (`--source-process:publish:`).
- `image-publish` as its own stage, versus a `publish` submode of `image-process` (`--image-process:publish:`).
- `execute-remote` as its own stage, versus an `execute-command` submode of `deploy-settings` (`--deploy-settings:execute-command:`).

Neither `source-process:publish` nor `image-process:publish` exists — their only occurrences anywhere are the `?` annotation lines in the sketch itself. Neither does `image-publish` or `execute-remote`. Nothing in the tree answers any of the three questions.

`source-publish` is the one of the three that has been given a stage name: it is in the `AllBuilders` filter, in `HelpSelectStage.include`, and in `README.md`'s stage table. It also has no builders and no runner, per the stage list above. Both halves are present fact; neither is a decision, and the question stands open exactly as the other two do.

Mention counts above are files under `ws-myx-devops/source/`, excluding `.git`, compiled `bin/`, and `readme.txt` itself. Builder counts are the files in the builder directories themselves.

## Learn syntax from --help/README, not from reading source — default, not fallback

Before invoking any `sh-scripts/*.fn.sh` command you haven't run this session, get its documented interface first: `Help` inside the relevant console for the roster, `<Verb> <Name> --help` for one command's short syntax, or its `Help.<Name>.help.md` full manual (same `sh-lib/help/` pair convention as myx.common). Check the owning package's `README.md` too when one exists. Only fall back to reading the `.fn.sh` source itself when the help/README genuinely doesn't answer the question (or when the task *is* modifying the tool, which is the owning `keeper-*`'s territory anyway) — treat source-reading as the fallback, not the default first move. `ShellTo.fn.sh` takes a positional `<project-keyword>` argument, not `--select-projects`/`--execute-command` flags (that's `ExecuteParallel`'s shape, not `ShellTo`'s) — guessing this from a source skim instead of checking `--help` risks a live SSH-target lookup error against a real host. A multi-word remote command is trailing bare words after a literal `--` (`ShellTo <selector> --ssh-user root -- ae3 status`); passing it as a quoted `--execute-command "ae3 status"` value instead mis-escapes downstream and the remote `ssh` invocation rejects it as an illegal option.

## The console entry points — one tool family, every non-Eclipse workspace

Every non-Eclipse multi-root workspace is itself built and operated by this same `myx.distro-*` tooling — see the owning `partner-*` for any namespace-map side. A workspace root can carry a set of thin launcher scripts, each dropping into an interactive `Distro <verb>` shell or accepting a piped command via `--non-interactive`:

- `DistroSourceConsole.sh` — source sync/prepare/ingest (`Distro DistroImageSync --all-tasks --execute-source-prepare-pull`, `Distro DistroSourcePrepare --ingest-distro-index-from-source`, `BuildCachedFromSource.fn.sh`)
- `DistroLocalConsole.sh` — local tool management (`.local/myx/myx.distro-.local/sh-scripts/DistroLocalTools.fn.sh --upgrade-installed-tools`)
- `DistroDeployConsole.sh` — deploy-side operations (`BuildDistroFromSource.fn.sh`, etc.)
- `DistroRemoteConsole.sh` — remote operations

Which subset exists tracks the workspace's purpose: a personal/refactor-only workspace may carry Source and Local alone, while `ws-myx-devops` is the fullest reference instance and carries them all, with `actions/distro/{source,source-tools,local-tools,deploy,deploy-tools,remote-tools,system-tools}/` alongside it — read there before assuming a console's full command vocabulary, since no single workspace's subset shows the whole picture.

**VS Code integration is a fixed pattern**: each workspace's `.code-workspace` file wires `⌘⇧B` entries straight to these consoles, non-interactively, e.g. `bash -c 'echo "Distro DistroImageSync --all-tasks --execute-source-prepare-pull" | .../DistroSourceConsole.sh --non-interactive'`. Recognize this shape on sight.

**What actually (re)generates `<workspace-name>.code-workspace`**: `DistroSourceTools.fn.sh --make-code-workspace [--quiet]` (implementation: `myx.distro-source/sh-lib/SourceTools.Make.BuildCodeWorkspaceData.include`), run through `DistroSourceConsole.sh` — not a per-workspace `install-<workspace>-workspace.sh` bootstrap script. Those bootstrap scripts exist only for one-time setup on an unprepared machine — they fetch and run `myx.distro-.local`'s generic `workspace-install.sh`, declare namespace roots, pull the initial git repos, and may set one-time settings like `MDLT_CONSOLE_ORIGIN` — but contain no `.code-workspace`-writing logic themselves. `--make-code-workspace` is a pure regenerate-from-current-state operation (re-derives the folder list live from `--list-namespace-roots`, `cat >` overwrites the file wholesale, `ln -sfn` for the generated `.local/.vscode/{browse,status}` symlink trees) — safe to re-run any number of times, Tier 1 by this file's own test (regeneration of a generated artifact), and it does **not** touch `MDLT_CONSOLE_ORIGIN`/`MDLT.settings.env` at all — that stays a separate, one-time `DistroLocalTools --system-config-option` concern. `DistroSourceTools.fn.sh` self-triggers `--make-code-workspace --quiet` after any operation that changes namespace roots. There's also `--make-rebuild-namespace-roots`/`--make-rebuild-repository-roots` (syncs `.local/roots/*.distro-namespace` and `source/*/repository.inf` against what's actually on disk — the input `--list-namespace-roots` reads) and `--make-workspace-integrations` (runs all `--make-*` commands together). **Reorg/migration takeaway**: after moving, adding, or removing a namespace root or project directory, re-sync with `DistroSourceTools --make-rebuild-namespace-roots` then `DistroSourceTools --make-workspace-integrations` (or just `--make-code-workspace` for the workspace file alone) — don't hand-edit `.code-workspace` and don't expect the one-time bootstrap installer to regenerate it.

**How a console's dispatcher actually works, confirmed from real source (`console-source-bashrc.rc`, `console-.local-bashrc.rc`), not to be re-derived each time:**
- `DistroSourceConsole.sh`/`DistroDeployConsole.sh` each run `bash -i --rcfile <package>/sh-lib/console-<name>-bashrc.rc`, which defines wrapper functions (`Source(){...}`, `Deploy(){...}`) that: strip a trailing `.fn.sh` off arg 1, `type`-check whether that name is already a shell function, and if not, `source` (`.`) the matching `sh-scripts/<Name>.fn.sh` file — each `.fn.sh` file's own convention is to define a same-named shell function as a side effect of being sourced — then call that function with the remaining args. `Help()` is also defined, printing the console-wide overview of the verb wrappers that console defines (`Action`/`Require`/`Source`/`Deploy`/`Distro` listed together) — a wrapper roster, not a statement about which families that console's `PATH` carries.
- `DistroLocalConsole.sh` runs `bash -i --rcfile myx.distro-.local/sh-lib/console-.local-bashrc.rc`, which is the base/hub layer: it puts every installed package's `sh-scripts/` on `PATH`, but defines **no `Local()` wrapper** — `.local`'s own `.fn.sh` files (e.g. `DistroLocalTools.fn.sh`) are invoked as bare executables directly, not through a verb function. Instead it defines `SourceConsole()`/`DeployConsole()`/`RemoteConsole()` — each spawns a *nested* `bash -i` under that other console's own rcfile, for when the fuller interactive environment is actually needed.
- **Practical upshot**: each console's rc hardcodes its own list of package `sh-scripts/` directories, of the shape `$MDLT_ORIGIN/myx/myx.distro-<family>/sh-scripts` (`$MDLT_ORIGIN` resolving to the source tree when the console runs from source, the installed tree otherwise) — one per installed family, no dynamic discovery. A family on that console's list is reachable there as a bare `<Name>.fn.sh` regardless of wrapper functions, so the `Source`/`Deploy` wrapper is same-shell convenience (avoids a subprocess spawn) rather than a required indirection — but the lists differ console to console, so console choice genuinely can put a family out of reach. Which families the open console carries is read from its own `PATH`; the check itself and what a missing name means are `magic-devops.armed.md`'s own Domain-knowledge rules.
- **The verb wrappers differ only in reach**: `Distro` resolves a name across the whole console `PATH`; `Source`/`Deploy`/`Agents` are the same wrapper shape pinned to their own package's `sh-scripts/`. Each sources the resolved `.fn.sh` into the session only when a function of that name is not already defined, then calls that function — which is why a name stays bound to the session's first-loaded copy until the console is replaced.
- **The actual "Update Local Tools" invocation**: `DistroLocalTools.fn.sh --upgrade-installed-tools`, run bare inside `DistroLocalConsole.sh` (or any other console carrying that family, per the PATH point above) — help pair `Help.DistroLocalTools.help.md`/`.include` under `myx.distro-.local/sh-lib/help/`.

### Console `PATH` is hand-authored — the templating layer stops one layer short of it

**`console-*-bashrc.rc` files are hand-authored, not generated.** No `console-<name>-bashrc.rc` carries a "generated by"/"DO NOT EDIT" marker anywhere in it; each instead carries an editor-hint header, `# ^^^ for syntax checking in the editor only`. The family `PATH` lists inside them are asymmetric and hand-varied per file — each console's rc lists its own family first, then differs in what it appends after — not the output of one shared template.

**The real templating layer stops one layer short of that content.** `--make-console-command`/`--make-console-script` (`SourceTools.Make.include` and its per-family siblings) regenerate only the thin launcher wrapper — `DistroSourceConsole.sh` etc., a `cat <<-'DISTROCONSOLE'` heredoc whose entire body is `bash --rcfile <the-hand-authored-rc> -i`. Nothing in that op touches the rc file's own `PATH`-building content; the wrapper is regenerated, the rc it invokes stays hand-authored.

**No existing op regenerates console `PATH` from `project.inf Declares:` today.** That would be new capability. It fits the established `--make-*` = regenerate-derived-artifact-from-current-state pattern already used elsewhere in this family (see `--make-code-workspace` above) — natural shape: a new `--make-console-path`-style op, chained into `--make-workspace-integrations` alongside the others.

**`--install-workspace-integrations` (`DistroAgentsTools.fn.sh`, `myx.distro-agents`) is not that op** — don't confuse the two. It's agents-domain-specific: VS Code settings plus skillset-symlink installation, keyed off the `magic-team:team-member:*` tag. Unrelated capability that happens to share the word "integrations" with the `--make-*` family above.

**The `<stage>:<submode>` tag convention (`image-prepare:...`, `image-install:...`, etc. — see "`stage:submode` is the mechanism already in production" above) does not fit a console-`PATH` tag.** Confirmed by reading `image-prepare`'s real 5 builders (`BuildDistroFromSource.fn.sh`'s own chain, described above under "A stage is a runner"): they exist purely to turn `source`+`cached` into a deployable `distro`/`export` tree for CI/batch publish — zero relationship to an interactive developer console session. A bare, non-stage-scoped tag is the right shape for a console-`PATH` tag instead.

**Real precedent for a bare, non-stage-scoped `project.inf` tag**: `magic-team:team-member:skillset/keeper-myx:*` (`util.workspace-myx.devops/project.inf`, consumed directly by `AgentsTools.Install.include`'s `--install-skillset-symlinks` arm) and `build-tool:pack.jar` (`myx.distro-deploy/project.inf`, backed by a `make/pack.jar.inf` recipe file consumed by the generic packaging machinery). Both bare, both consumed by a named tooling op rather than a pipeline-stage builder — the same shape a console-`PATH` tag would need.

**Settled, not yet implemented: `custom-commands-path:sh-scripts`.** The tag a user-added custom project would declare via `Declares:` (self-only, non-inherited, per `Man.Project.Inf.file.help.md`'s own schema) to contribute its own `sh-scripts/` to console `PATH` — additive only, never touching the existing hardcoded embedded-family `PATH` lists. Full decision record: `board/backlog/interview-20260821T2331Z-project-specific-commands-on-path.md`, "Settled, approved" section.

**Per-workspace `.local/` is the installed tool release** — `myx/` holds the installed `myx.common`/`myx.distro-*` packages themselves, alongside `roots/`, `assets/`, `home/`, `lib/`, `agents/`, plus `MDLT.settings.env`/`MDSC.source.settings.env`. Written by the console commands above through their own install/upgrade path; never hand-edited. Not a generated tree, not a cache, not regenerable by us — see `magic-devops.armed.md`'s own `$MMDAPP/.local/` rules for why. Exceptions, genuinely generated and still Tier 1: the regenerable subtrees under it — `source-cache/`, `system-index/`, `temp/`, and `.cleanup/` (`--purge-cleanup`'s own target). The release-version rule above is about `.local/` as a whole, not about those.

**Overlap with the owning `partner-*`, not a clean line**: this skill owns the tool itself — consoles, sync/index/build machinery, task wiring, `myx.distro-*` package internals. `myx.distro-*` is deliberately extensible — any project can declare its own `.fn.sh` functions, custom builders, and `ExecuteParallel.fn.sh`/`ExecuteSequence.fn.sh` targets selected via `--select-merged-keywords`/`--select-projects`. Once a project extends the tool this way, the extension is simultaneously "tool mechanics" (this skill) and "domain content" (the owning `partner-*`) — use both lenses. The one thing unambiguously that `partner-*`'s alone: the actual namespace inventory data (`infra/accounts-<ns>`, `clusters-<ns>`, `instances-<ns>`, etc.).

**`ExecuteParallel.fn.sh` gotchas**: must be invoked through a console dispatcher — `echo "Deploy ExecuteParallel ..." | ./DistroDeployConsole.sh --non-interactive` from the workspace root — not run as a bare script; outside the console's PATH setup its own project-selection dispatch fails with `unknown command: ListDistroProjects`. **Argument order is load-bearing**: `--ssh-user`/`--ssh-host`/`--ssh-port`/`--ssh-home`/`--ssh-args`/`--no-sleep`/`--non-interactive`/`--execute-post-process` must all come *before* `--execute-command`/`--execute-script`/`--execute-stdin`/`--display-targets` — the ssh-option parser is a `while`/`case` loop that stops at the first token it doesn't recognize, so flags placed after the execute-type flag silently leak onto the remote command line instead of being parsed.

**Invoke through the console dispatcher, always**: `echo "Deploy ExecuteParallel ..." | ./DistroDeployConsole.sh --non-interactive` (or `Source`/`Local` equivalents), not `bash sh-scripts/Foo.fn.sh` directly. The console's bashrc puts all `sh-scripts/` dirs on `PATH` before handing off to the dispatcher; without it, a nested `Distro <name>` call to a command that isn't already sourced fails with `unknown command: <name>` even though the file exists.

**`ShellTo` for remote diagnosis — batch into one call per host.** Run ONE `bash`/`sh -c` invocation per host that does everything needed, never a separate console call per command — each separate invocation opens a brand-new SSH connection and re-runs the whole console bootstrap (several seconds of noisy MISSING-provider warnings every time). Don't use `ExecuteParallel` for investigation/ad-hoc work — use `ShellTo` targeted at the single project, since `ExecuteParallel`'s default ssh identity may not be the one that works; `--ssh-user root --ssh-home ~/.ssh` is a common working override. This same batching principle generalizes to every local console session too — see `magic-team`'s `magic-team.armed.md`, "Team-Member's (-specific) tooling" section, for the full technique (session-worthy rule, sentinel-based completion detection, lifetime/ownership). This skill operates sessions against `ws-myx-devops` (checks) and prv-farm assets.

**An MCP-wrapped shell-execution tool can stay pinned to its own configured workspace root — a `cd` prefix inside the command string does not move it.** Confirmed: `cd <other-workspace> && ./DistroDeployConsole.sh ...` run through such a tool still resolved `Deploy --info`'s `MMDAPP ROOT` to the tool's own configured workspace, so every project-selector lookup against the other workspace failed with "No matching projects found" even for an index-confirmed exact path; the identical command run through a plain (non-MCP) shell-execution tool resolved correctly. When operating a console against a workspace other than such a tool's own configured root, use a plain shell-execution tool instead.

**`ScreenTo.fn.sh` needs a real TTY.** It resolves the project and builds a valid SSH connect command — SSH auth itself can succeed — but then fails with "Must be connected to a terminal" when the caller has no pty (e.g. a non-interactive agent sandbox). Use `ShellTo` for a single command when no real terminal is available; reserve `ScreenTo` for genuine interactive sessions.

**Parallel-sweep unit of work, live-fleet multi-node inspection: capture AND parse entirely server-side.** One ssh session per node runs the capture/parse pipeline (e.g. `tcpdump | perl/awk`) on the remote box, and only the final reduced result is pulled back — never stream raw capture output over SSH for many parallel probes, which is slow and wastes bandwidth/tokens. The correct unit of parallelism is one file per node/server (every interface a node needs captured, merged server-side into that one file) — not one file per (node, interface) pair, and not one file per (node, account): per-account fan-out causes an N-times-SSH-connections blowup.

**Keep-Alive Console Session (`--console-start`/`--console-send`) `-- <command...>` form re-tokenizes and loses embedded newlines/quoting — use the heredoc/stdin form for anything multi-line.** `--console-send <channel> -- bash -lc '<multi-line body>'` looks like it passes one quoted argument, but the caller's own shell has already split it into positional args (`bash`, `-lc`, `<body with real newlines>`) before `DistroAgentsTools.fn.sh` ever sees it; the FIFO writer then does `printf '%s\n' "$*"`, which space-joins those args back into one line and writes it verbatim. The console's own reader is one persistent `bash -s` consuming the FIFO as sequential top-level input, not a fresh shell per send — so what it actually receives is `bash -lc` on its own line (the newline that should have stayed inside `-c`'s quoted argument instead terminates it), producing `bash: -c: option requires an argument`, and then every subsequent line of the intended script runs as flat top-level statements directly in the console's persistent shell rather than inside the intended nested login shell. This is silent — real output still often appears right after, so the failure mode is easy to miss across many rounds. Fix: use the heredoc/stdin form instead — `--console-send <channel> <<'EOF' ... EOF` (no `--`, no command after the channel) — which hits the FIFO writer's `cat > "$fifo"` branch and preserves real newlines/quoting untouched. Also note: `--console-send` has no `--from-stdin` flag — passing one sends it as a literal (failing) command into the console; the heredoc alone is what triggers stdin mode.

**`myx.common lib/parallel` vs. plain shell background jobs.** `lib/parallel` works well for fanning a command across stdin-provided arguments with a worker cap, but for a full-fleet sweep across only a handful of nodes (~6), plain shell background jobs (`cmd & ... wait`) are simpler and sufficient. `lib/parallel` earns its keep at large item counts (dozens+), not a handful of servers.

**Hand-rolled action scripts (`DeployRouting.fn.sh` and similar project-local `.fn.sh` wrappers, as distinct from the core `sh-scripts/*.fn.sh` building blocks) typically have no built-in dry-run/`--display-targets` flag.** Their argument parsing is usually a small hand-written `case` statement; any flag it doesn't explicitly recognize falls through toward the script's real, mutating body rather than into a safe no-op — there is no generic convention guaranteeing a preview mode exists. Don't guess a flag name and invoke the script itself to "just see what it would do." Instead, read the script and replicate its own internal target-resolution logic as a separate, pure read-only call — typically a `ListDistroProvides`/`ListDistroProjects` invocation using the same `--select-merged-keywords`/`--filter-*-provides-column`/`--filter-*-column` arguments the script uses internally to build its task list — which shows exactly what the mutating run would target without ever reaching the SSH/apply step.

**When authoring a new action/wrapper script by copying a sibling's structure (e.g. a settings-apply wrapper copied from a working routing-apply wrapper), don't carry over its selector flags (`--select-merged-keywords <value>` or similar) without independently verifying the correct value for the new script's own target set.** Structurally identical wrappers can front genuinely different deploy mechanisms with different real targets — an SSH config-apply script and an rsync-style file-sync script, for instance — so a keyword that correctly scopes one can silently under-select for the other: no error, just a quietly incomplete target list (a host present in the real intended set simply never appears, with nothing to indicate it was dropped). Always independently verify a new wrapper's selector against the actual `Keywords:` field of the specific `project.inf`(s) it's meant to target — via the same read-only `ListDistroProjects`/`ListDistroProvides` resolution check described above — rather than assuming it matches a sibling wrapper's value.

**When scanning full output from a live multi-host deploy for problems, grep broadly across the entire output rather than sampling or trusting a summary line.** Search for `error|fail|denied|refused|timeout|no route|exit code|connection refused|permission denied` (case-insensitive) across the whole log, not just the tail. Pre-existing, unrelated warnings (e.g. stale-index `MISSING:` provider gaps for projects that have nothing to do with the deploy in question) routinely coexist with an otherwise fully clean run — don't mistake them for new problems, but don't assume a run is clean without actually running the broad scan either.

## Index/provides mechanics: the live lookup path and the cached-snapshot path are different files

Two genuinely separate mechanisms exist in the index system, feeding different consumers — conflating them leads to treating a stale report file as if it were a functional outage, or vice versa:

- **The live, no-cache lookup path** — `IndexNoCacheDistroProjects`, driven only by `source-cache/all-projects.index.txt` (a lightweight project-path listing). It reads each selected project's `project.inf` fresh, on every call. This is what selector-based queries (`ListDistroProvides --select-*`/`--filter-*-column`, and by extension what `DeployRouting.fn.sh`/`DeploySettings.fn.sh` read internally to build their task lists) actually consult at runtime. As long as `all-projects.index.txt` itself is current, this path is always current — it never goes stale independently, because it doesn't cache the provides data at all.
- **`all-projects.index.txt` itself is not automatically current after a project move.** It only reflects reality as of the last time `DistroSourcePrepare --ingest-distro-index-from-source` (or equivalent) was run — a project move/relocation that lands correctly on disk and is committed/pushed can still leave `ListDistroProvides --select-projects <name>`/other selector-based resolution returning the pre-move path and pre-move `Provides:` entries, with no error, until that command is re-run. Confirmed directly: a project relocated on disk (old path removed, new path present with its `project.inf`) still resolved under its old path via `ListDistroProvides` until `--ingest-distro-index-from-source` was re-run, after which it picked up exactly that one changed project and resolved correctly. Practical implication: after ANY project move, re-run `DistroSourcePrepare --ingest-distro-index-from-source` before trusting a `ListDistroProvides`/selector-based resolution check — don't assume the live-lookup path is automatically fresh just because it isn't the cached-snapshot pipeline described below.
- **The cached-snapshot pipeline** — `DistroSourcePrepare.fn.sh`'s `--sync-cached-from-source` writes `source-cache/prepare/distro-provides.txt` (and sibling `distro-declares.txt`/`distro-keywords.txt`/`distro-requires.txt`); `--ingest-distro-index-from-prepared` publishes that into `system-index/distro-provides.txt`; `--build-project-metadata` rebuilds the same aggregate from per-project cache subdirectories. This is a separately-maintained report/aggregate artifact — nothing in the live selector-query path reads it. Staleness here does not imply staleness in the live lookup path above, and does not by itself indicate anything is broken for an actual deploy — verify which of the two mechanisms actually feeds the operation in question before treating a stale file as a functional problem.
- **The index-rebuild pipeline has a required step order.** `--scan-source-changes` must run first — it's what populates `source-cache/new-changed.index.txt`, the change-delta file every later step gates on. `--sync-cached-from-source`, `--rebuild-cached-index`, and `--build-project-metadata` all silently no-op (`"no new changes"`) or produce incomplete/partial output if run without `--scan-source-changes` having populated that delta first, and none of them surface an error when this happens — a partial `--build-project-metadata` run manifests as `cat: ... No such file or directory` for whichever projects' per-project cache subdirectories were never created. Correct full sequence when the cached-snapshot files themselves need refreshing: `--scan-source-changes` → `--sync-cached-from-source` → `--build-project-metadata` → `--ingest-distro-index-from-prepared`.

## Building blocks vs. actions — two different layers, don't conflate them

**The building blocks are the dispatchable `sh-scripts/*.fn.sh` commands themselves** — `ExecuteParallel.fn.sh`, `ExecuteSequence.fn.sh`, `BuildDistroFromSource.fn.sh`, `DistroImageSync.fn.sh`, `DeployRouting.fn.sh`, `BuildCachedFromSource.fn.sh`, and the rest of each package's `sh-scripts/` tree. Each one is documented exactly like a myx.common command: a `Help.<Name>.include` (short syntax) + `Help.<Name>.help.md` (full manual, rendered the same `myx.common lib/catMarkdown` way) pair under the owning package's `sh-lib/help/`, invoked as `<Verb> <Name> [args]` through a console (`Source`/`Deploy`/`Local`/`Remote`). **Run `Help` (or `<Verb> --help`) inside the relevant console to see the current roster** — same "check the documented interface before reading source" discipline as myx.common itself. These are what you compose when building something new.

**`actions/**` is the opposite layer: complete, proven, predefined pipelines, not raw material.** Confirmed directly from `myx.distro-deploy`'s own README folder-mask table: `actions/** - usable actions (predefined parameters for other scripts)` — a per-project, hand-authored fixed parameter set already bound to one of the building-block commands above. The workspace-root `/actions` tree (of the shape `actions/<category>/<script>.sh`) is explicitly documented as **"workspace actions - executable, non-editable (generated)"** — a flattened, aggregated view of every project's own `actions/**`, not something to decompose or chain further.

**Which layer to reach for is decided by the caller, not by which is better.** An action exists so a person, or a task-menu binding, can fire a prepared parameter set without assembling one; when that is the caller, running the existing action directly beats re-deriving the equivalent `sh-scripts` invocation. A member doing the work calls the building block instead, because the work requires knowing which tool ran and with which parameters, and an action hides both. Composing the real building blocks is also what you fall back to when no action covers the job — the confirmed chaining idiom is a build command followed by a fleet-execution command, or `ExecuteSequence.fn.sh ... \; sleep 30` for a rolling restart between hosts.

## Baseline ownership of lib/myx/acm namespace roots, wherever they appear

`lib`, `myx`, and `acm` are namespace roots this skill has at least minimal maintenance responsibility for regardless of which workspace they're checked out in. They are registered as namespace roots inside other namespace-family workspaces too — present as registered `repository.inf` placeholders, just not populated — so a `lib`/`myx`/`acm` question doesn't become the owning `partner-*`'s just because it's asked from inside one of those workspaces.

- `myx` is this skill's core territory everywhere (myx.common/myx.distro-* tooling itself).
- `lib` (vendored third-party dependencies) is general dependency/build/packaging maintenance — this skill's baseline.
- `acm` (AxiomCMS) is narrower: the `.tpl`/skin templating content itself belongs to the owning `keeper-*`, but general repo-level build/package/CI plumbing for `acm` falls to this skill at baseline. Defer to that `keeper-*` the moment the question touches `.tpl` files, `skin.settings.xml`, or the `<% %>` template language.
