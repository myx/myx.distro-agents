## Two shell standards, and which one a file is held to

The same three platforms — Darwin, FreeBSD and Linux — produce two different standards, and a file is held to exactly one of them. What the file itself requires settles which one. What it happens to run on does not.

- **A `bash` script is written to bash 3.2**, the crossplatform baseline version across Darwin, FreeBSD and Linux. A file that already declares a bash requirement is written against that version's own feature set, not contorted into POSIX. The constructs are available to it, subject to the test below.
- **An `sh` script is written with no bash-isms at all**, because all three platforms' own `sh` has to run it. A construct is rejected there for being a bash-ism, not for failing somewhere: it stays out even where it would work on Linux. Test such a file under `dash`, never under `bash --posix` — that still accepts `<<<`, `[[ ]]` and arrays, so it passes a file `dash` rejects outright.
- **macOS `/bin/sh` is bash 3.2, not an independent shell**, so a test there proves nothing about POSIX behaviour. `/bin/dash` on macOS is Apple's dash. FreeBSD's `ash` cannot run offline. An include written with `done < <(...)` cannot be sourced under dash, so a check of one function cuts that function's text out and runs only that.

The two tests point opposite ways, which is why the standard is settled before the code is written rather than argued per construct.

**What executes a file settles this, not the line at the top of it.** A shebang is an interpreter line only where something reads it as one. A body embedded into a larger script and evaluated inline runs under whatever is actually running it. So does a file passed as an explicit argument to an interpreter. In both, their own first line is inert text. A generated installer that concatenates fragments and runs the result under a named interpreter produces both cases at once. It can carry more than one inert shebang. Read the mechanism that runs a file before deciding which standard it is held to. A file whose shebang is never consulted has been held to the wrong standard by everyone who read only the shebang. Nothing surfaces the error, because the code keeps working.

### The bash 3.2 baseline, and what follows from it

The baseline is the rule. The exclusions are derived from it, not memorised beside it. A flat list of banned builtins invites the next bash-4 feature to slip in for not being on the list. Anyone applying the baseline reaches the same exclusions unaided.

Available: redirections, expansions and arrays — process substitution `<( )`, herestrings `<<<`, indexed arrays with `+=( )`, `[[ ]]`, pattern substitution `${var//x/y}`, `local`, `$'...'`.

Excluded, as is everything else bash 4 or later added: `mapfile`/`readarray`, associative arrays (`declare -A`), case conversion `${var^^}`/`${var,,}`, `declare -g`.

**Availability is not a reason to use anything.** A bash 3.2 construct goes in only where it makes the result better on all three counts:

- **faster (executionally, less CPU time, less total time)** — two measures, and both have to improve. A construct that cuts CPU while adding waiting is not faster, and neither is one that cuts elapsed time by spending more CPU. Fewer lines is not evidence of either.
- **readable (understandable, traversable by eye)** — two things at once. A reader has to understand what it does *and* scan it without stopping to decode. A dense one-liner can be understandable after study and still fail the second half.
- **simpler (logically, algorithmically solution-wise)** — reaches past the code to the solution. Not only fewer branches in what was written, but a less elaborate approach to the problem. Not line count, and not `readable` restated.

Any one of the three failing is a reject, and the plain form stands.

`simpler` is the criterion that catches what the other two miss. Its algorithmic half is the harder failure to see, because the code can look clean. Take a scan captured into one variable, an extraction captured from that, and a file holding the same rows. Each stage is understandable and traversable line by line. It is still a three-stage approach to a one-stage problem, which a reviewer judging only the code's tidiness would pass. `readable` asks whether a reader follows this line. `simpler` asks whether there is less to follow at all, and whether the solution needed these steps.

In review the question is never whether 3.2 allows a construct. It is those three questions, and all three answer yes or the construct comes out.

### Shell features and external tools are different constraints

Both exist because the same three platforms are supported, and they resolve in opposite directions:

- **The shell's own features** are granted by the version floor above. A file declaring bash gets bash 3.2's syntax.
- **External utilities** differ per platform, which is what rules out `grep -P` and in-place `sed -i` (see Principles below). That says nothing about the shell's own syntax.

This distinction exists to stop one mistake: writing POSIX-only shell inside a bash script, to satisfy a constraint that is really about `sed` and `grep`.

### Which language a piece of tooling is written in

Take the first that does the job well, in this order:

- **bash 3.2+**, where bash is efficient and fast for the task. A per-record transform whose bash form forks a process per line is not efficient, so it is awk.
- **awk**, wherever possible over Python.
- **Python**, only where it is required and awk won't do it, or would be utterly inefficient. A JSON-shaped task tries `jq` before Python.
- **Perl** is not used: between the two, Python is the chosen one, for now. The team keeps one of the two, never both. Switching means replacing every Python file and installing Perl everywhere. So it needs proof that Perl is universally better, put to the human-owner on his direct channel.

No choice adds a new runtime dependency. The tool is chosen for the file it is expected to grow into after the first MVP, not for its first version. That counts the complications and improvements that follow: edge cases, error handling, new options. The order applies when a file is written. It also applies when a task already changes the file for its own reason: a defect, a dependency to drop, an owner ruling. It is never a reason to convert working code by itself, and never a sweep. Working code is kept until it is clearly a laggard (too slow) or a blocker (stops needed work), or the human-owner rules otherwise. The call site says why a later tool was needed.

## A scratch file is the most expensive name in a shell script

Written to the bash standard: the process substitution below is a bash-ism, and `dash` rejects it outright with `Syntax error: redirection unexpected`. What earns a file is the same under either standard. The mechanics here are bash's.

- A value that fits in a variable goes in a variable. A file additionally costs a path to construct, a `mkdir -p`, a creation-failure branch, an EXIT trap and an `rm -f` on every return path. That machinery's whole purpose is to undo the file.
- Where a file is not earned, `<<<` carries the data and no file of yours is written. Where one is earned to replace an existing file, it is created beside that file and renamed over it. The rename is then a same-filesystem `rename(2)`. A temp in the system temp directory trades that atomicity for a cross-device copy. Beyond those two points the spelling varies between working sites of a single project: the temp's name, `mv` against `mv -f --`, a trap, an asserted mode. That variation is not a defect to normalise. One spelling is out whatever the surrounding style: **a hand-written path under `/tmp`**. A temp is created beside its target with `mktemp "$target.XXXXXX"`, or with `mktemp -d "${TMPDIR:-/tmp}/<name>.XXXXXX"` where a directory is genuinely earned. `mktemp` always takes an explicit path template. On Darwin (macOS 26) a bare call, `-t` and `-d -t` all ignore `TMPDIR`, so the file lands where no scan of `TMPDIR` finds it. A literal path assembled from a fixed directory and a name the script chose collides between concurrent runs. It survives a crash as litter. On a shared host it sits somewhere every other user can reach.
- **Under bash 3.2 a here-string is a real file, created and unlinked before the reader opens it.** Measured on bash 3.2.57, Darwin 25.5.0. `stat -f %HT /dev/fd/0` reports `Regular File` for `<<<"probe"`, against `Fifo File` for a pipe, which is the control. Bash writes it to `/private/var/tmp/sh-thd-<digits>` with mode `0400`, then unlinks it. While the descriptor is open, `lsof` still names that path and `stat` on that exact path already fails, so the directory entry is gone before the reader looks, and no other process can open it by that path. Two limits follow. `TMPDIR` is not honoured: pointing it elsewhere moved nothing, while `mktemp "${TMPDIR}/x.XXXXXX"` honoured it in the same shell. The write is real filesystem I/O, so a here-string is not the free path it looks like beside `mkdir` and `rm`. Measured on Darwin only: Linux and FreeBSD were not read for this.
- **An existing temp-file form is never converted into another.** A new site takes the form its own file already carries, or the nearest one in its own package. A site that already works is left alone. This is where the substitution actually happens: a general recipe looks safer than whatever is there. So the working line is rewritten into it for no behavioural gain. An expansion swapped for a fork is slower as well.
- An EXIT trap is not the safety net it looks like **inside a function**. That trap is the process's, so it silently replaces a caller's. Its own `trap - EXIT` clears that one too. Measured: a caller's EXIT trap never runs once a function it calls sets its own. The function's trap fires at process exit, not at return. **Inside a `( … )` subshell it is sound.** The same measurement shows the subshell's trap firing at subshell exit, with the caller's still intact afterwards. That makes `( tmp=$(mktemp "<target>.XXXXXX") ; trap 'rm -f -- "$tmp"' EXIT ; … ; mv "$tmp" "<target>" )` a correct temp-file idiom rather than a leak. It holds provided no caller holds `tmp` as a `local` (next bullet). `<target>.$$` is not this idiom: every subshell of one shell shares its process id, so two writers of one call can collide on it. The same reasoning applies to a kept pid used later to signal a process. It is never signalled by its bare number alone, only while it is still the process that began then, since pids come round. A file whose cleanup instead depends on every exit path reaching an `rm` is a file that was not earned. Under `set -e` that dependency is worse than it looks: the shell aborts on the failing command itself. An `rm -rf` written after it is then unreachable on exactly the runs that leave the mess it was there to clear.
- **A `( … )` subshell's EXIT trap never names a function local.** Measured on bash 3.2.57, where the call runs from a string (`eval` or `bash -c`). Take a subshell there that ends other than by reaching its last command: by an explicit `exit` or a `set -e` abort. It drops the function's locals before the trap runs. The trap then expands the name to empty and cleans up nothing. The same call from a script file keeps the value. A subshell behind `||` never takes the `set -e` abort, because `set -e` is off there. So the runs a reviewer usually tries pass. A `$( … )` substitution keeps it in every shape measured. Bake the value in when the trap is set: `trap "rmdir $( printf '%q' "$lockDir" ) 2>/dev/null || true" EXIT`. Never copy it into a subshell variable, which a caller's `local` of the same name breaks again.
- A file feeding a loop disappears entirely under process substitution: `while IFS= read -r line ; do … ; done < <( … )` — no path, no trap, no cleanup, and no exit status. On bash 3.2 `PIPESTATUS` holds the read loop's own status, the same value a `< /dev/null` loop leaves. `wait "$!"` reports the substitution is not a child of this shell. A producer status that has to be tested needs a real pipeline. Its `PIPESTATUS[0]` holds the status, and its loop body runs in a subshell that keeps nothing it sets.
- One dataset is materialised once. A capture, a second capture derived from it, and a file holding the same rows are three copies of one pipeline's output. Each pays for its own declaration, failure branch and removal.
- Two reasons genuinely earn a file, and both are about what the file *is* rather than about holding a value:
  - **A real file another process must open** — and a credential is not that case, however much it looks like one. A header file takes the token out of `argv` and puts it on disk, where a mode on the file does not take it back. `curl -H @-` reads the header from stdin, so `<<<` hands it over with no file of yours to create, name or clean up.
  - **A whole document buffered before any of it is emitted.** A run that fails partway then leaves nothing on stdout that reads as a finished result. It only works if every byte is written inside the redirect: one header printed before the redirect defeats the entire mechanism.

### Worked example: a temp dir with a trap against `<<< "$( … )"`

Take a producer whose whole output a consumer reads once. Set a `mktemp -d`, several files inside it, a trap and an `rm -rf` beside a herestring fed one command substitution:

- The apparatus exists only to get data from a producer to a consumer. It is a `mktemp -d`, several files inside it, a trap, an `rm -rf`, and the error branches each of those needs. `<<< "$( … )"` does the same job with none of it. Bash creates and unlinks that here-string's own small file, so nothing is yours to name, clean up or track.
- It scores on all three of the criteria rather than trading one against another. It is faster: one small temp file the shell writes and unlinks, and no forks for `mkdir`/`rm`. It is readable: the data flow is visible at the point of use instead of split across four places. It is simpler: there is no lifecycle at all, so nothing to reason about.

The dir earns its place only when it is genuinely one of the two cases above. Those are a real file another process must open, and a whole document buffered before any of it is emitted. It is never a staging area for a value that already fits in a variable.

## Principles

- **A comment costs lexing time on every source, and on bash 3.2 more than an executed no-op.** Measured on this estate's Darwin box, sourcing a 100-function include 2000 times. 100 comment lines add 160 µs per source under bash 3.2 and 45 µs under dash. 1000 add 1990 µs and 415 µs. The cost is linear in comment volume, against a byte-identical-copy noise floor of ±6%. The same file carrying 1000 executed `:` no-ops instead costs 1575 µs under bash 3.2, less than the 1000 comments. So a comment line is not free for not running. Dash reverses that order, at 1105 µs. On a file sourced on every invocation the count is paid every time, which is an argument for brevity the readability limits do not make.
- **All three platforms are fully supported — none is a fallback or a lesser target.** FreeBSD carries the majority of the servers this software runs on. Darwin is the majority of its users. Linux is fully supported alongside both. That gives a non-portable construct two distinct worst cases. A FreeBSD break hits the largest number of servers. A Darwin break hits the largest number of people. The three named platforms mean their current versions: the latest LTS Linux, the latest RELEASE FreeBSD, a modern Darwin. That set is a ceiling on effort as much as a floor on support. A construct that is sound on those three is portable enough, full stop. Don't contort code for an obsolete shell, an ancient utility or a long-superseded OS release. Don't add compatibility shims for versions outside that set. Don't reject a clean construct because some historical version lacked it. Testing on whichever platform you happen to be developing on proves nothing about the other two. Verifying a construct on Darwin and Linux does not establish it works on FreeBSD, and FreeBSD is where the servers are.
- **A file descriptor above 2 is not addressable as a path on all three platforms**: only `/dev/fd/0`, `/dev/fd/1` and `/dev/fd/2` are universal. Linux's `/dev/fd` is a symlink to `/proc/self/fd`, so every descriptor appears there. Darwin mounts `fdescfs` on `/dev/fd` by default, so it works there too. FreeBSD's stock `devfs` provides only those three. Anything higher needs `fdescfs` mounted on `/dev/fd`, which a stock install does not guarantee. So never hand a high descriptor to a tool as a path: `curl --data-binary "@/dev/fd/3"` is exactly this bug. Either avoid it, or guard it with a fallback the way `remoteContext.Common` does: `if [ -r /dev/fd/3 ]; then . /dev/fd/3; else eval "$(cat <&3)"; fi`.
- **No external/GNU dependencies**: assume only what's on a bare Linux/FreeBSD/Darwin base install. No GNU coreutils-isms (`sed -i` without a backup-suffix arg, `ls --color`, `readlink -f` on Darwin), no assuming a package manager has run. If BSD/GNU flag behavior diverges, write to the POSIX-common subset or split into `.Linux`/`.FreeBSD` files rather than special-casing flags inline.
- **`\|` alternation is a GNU BRE extension, and BSD `sed` reads it as a literal `|` rather than rejecting it.** Measured on this estate's Darwin box: `sed -n '/alpha\|beta/p'` prints nothing against a file holding both words, and exits 0. The same expression matches a line containing the character `|`. A pattern written that way therefore fails by matching nothing, with no error anywhere. A probe built on it returns the same negative for every subject on Darwin. That reads as a real finding rather than a broken pattern. `sed -E` gives ERE alternation on all three platforms, and is the portable spelling. `awk` is the other way out, since its regex dialect is ERE throughout.
- **BSD `grep` reads `\t` inside a bracket expression as a literal backslash and a literal `t`, so `[ \t]*` silently misses every tab-indented line.** The expression is accepted and the command exits cleanly, so the pattern fails by matching less than it names. Nothing distinguishes that from a file genuinely holding fewer matches. `[[:space:]]` finds space and tab alike on all three platforms and is the portable spelling. A count taken through the first form is a non-result, not a smaller result. It is withdrawn and re-taken, never reported as a lower number.
- **`find -exec` runs a command, and a `VAR=value` prefix on it is not an assignment.** Nothing parses a command line there, so the assignment is taken as the program to execute. The exec fails once per file, and the sweep completes reporting no match: a clean result that means nothing ran. Export the variable in the surrounding shell, or put the assignment inside an explicit `sh -c`, where a shell actually reads it.
- **Text inside a quoting construct is parsed by exactly one layer. Which layer it is settles the escaping, never which characters look special.** A payload assembled as one single-quoted bash literal ends at the first apostrophe anywhere inside it, whatever that apostrophe was for. An ordinary English possessive written into a JSON payload held that way closes the literal, and the file no longer parses. In the other direction, a quoted heredoc (`<<'EOF'`) expands nothing at all, so the shell's `'"'"'` idiom is not an escape there. Those six characters reach the inner program literally. An awk script spelling `task's` that way died on a syntax error at the word its author had tried to make safe. Name the layer that will parse the text before escaping anything — over-escaping and under-escaping are the same defect in opposite coats.
- **A quoted heredoc inside `$( … )` or `<( … )` has its body re-scanned, and one unbalanced quote or bracket there stops the file parsing.** Measured on bash 3.2.57, Darwin 25.5.0. A body holding `it's $HOME` exits 2 with `unexpected EOF while looking for matching '`. Removing the apostrophe is the control, and it passes. Balance is what counts, not presence: two apostrophes pass, and so does one apostrophe inside double quotes. An unbalanced `(`, `$(`, or backtick fails the same way. dash runs every one of those cases. So quoting the delimiter and writing literal content, exactly as advised, still fails on bash where ordinary English text is enough. Commands above the construct have already run when the error surfaces, so the run is half done. Read the heredoc into a variable instead, under bash: `IFS= read -r -d '' x <<'EOF'`. That takes the same body with no substitution around it, and it keeps the trailing newline that `$( … )` strips. It returns 1 even on a non-empty body, so guard it with `|| :` under `set -e`.
- **A heredoc body that carries the delimiter line itself ends the block, and the line after it runs.** Measured: a body holding `EOF` on a line of its own printed the `MALICIOUS-RAN` that followed it. With a checksummed delimiter the same text stayed inert. So an unguessable delimiter is not stylistic wherever the content is not trusted, and `myx.distro-deploy`'s `( eval "$( cat << 'BLK_<cksum>' … )" )` is the family form to copy.
- **Prose that has to live inside a shell literal is written to need no escape, not escaped.** `the team's own X` becomes `the X this team owns`: same meaning, and nothing downstream has to survive a quote. An invariant every instance happens to meet is not documented by them. Write it down where the next value is added.
- **A structural check that matches text never parses, so it reports clean over a file that cannot load at all.** A text-level check can report every expected site present for a file `bash -n` rejects outright. The two statements do not touch. Only the shell's own parser answers whether a shell file parses. Run `sh -n`/`bash -n` under the standard that file is held to. It costs one call and goes in front of any text-level check rather than after it.
- **A "nothing found" result is evidence of absence only if a positive control ran first.** Before trusting any recursive search's empty result, run the same command shape against a probe with a known answer, and confirm it comes back. Otherwise a genuinely clean tree and a search that never looked are indistinguishable, since both print nothing. The concrete trap is BSD `grep -r` on Darwin. It will not descend into a symlinked directory given as the search root, unless the path carries a trailing slash. It will not follow symlinked subdirectories met during the walk either. `-R` rescues neither case. A scan of a tree whose entries are symlinks into other filesystems therefore reports every file clean, having matched nothing anywhere. It never entered them, and the empty output looks identical either way. Use `find -L <root> -type f -exec grep ... {} +` for any recursive search over a tree that may contain symlinks: it follows both, and the trailing-slash difference stops mattering. Generalize past `grep` — any negative result offered as evidence needs a positive control through the same command shape before it counts as one. **A control is an instance of the exact class the pattern names, variants included.** A pattern written for an operator followed immediately by its argument does not see that same operator followed by a space. A control chosen without the space confirms only the half that was already matching. The sweep then reports zero for a class it never looked at.
- **A filter that never ran and one that found nothing print the same nothing.** The empty list is evidence of absence only once the filter's own status is read. A probe that ends in a filter which rejected its own arguments prints nothing, and reports that rejection only in its status. Measured on this estate's Darwin box: `grep -Et alpha` exits 2 with the pattern and subject both correct, because BSD `grep` has no `-t`. In a pipeline that member's status is not the pipeline's own. `printf … | grep -Et alpha | sed …` exits 0, and only `${PIPESTATUS[*]}` carries the filter's 2, as `0 2 0`. A later command that succeeds hides it the same way, since the script reports its last command's status. Read the matching command's own status before its empty output means anything, and treat a rejected argument list as a probe that never looked.
- **Inline builtins beat scattered vars/subprocesses.** Use parameter expansion (`${var%%pattern}`, `${var#pattern}`) and, in bash, `$'...'` quoting for a control character, inline. Not a var declared then matched in `case`/`esac`, and not a forked `printf`/`awk`/`head`. Smaller, faster, more readable. It is also the non-fragile choice. A multi-line quoted string or heredoc embedding a literal control character is the most fragile shell construct there is. Any autoformatter pass or reindent silently corrupts it, where `$'\n'` inline never can. (Separately, `$(...)` always strips trailing newlines — it can never hold "just a newline" for comparison. That's a correctness bug, not a formatting one.)
- **Read a field with the builtin, and reach for `cat` only where the value can hold a newline.** Measured on bash 3.2.57 (Darwin 25.5.0): 300 single-field files read with `IFS= read -r v < f` finished inside a second, and the same 300 through `v="$( cat f )"` took one. Both forms returned the value unchanged, so the fork is the whole difference. `read` returns 1 at a file whose last line has no newline, and 1 at a missing file, so the call needs `|| :` where either is possible: bare under `set -e` the missing-file case ended the shell at rc 1, and guarded it carried on at rc 0.
- **A heredoc takes one of two shapes, or it is not written.** Either its body sits at zero indentation, opened and closed at column one, in a file whose content is that body. Or it is simple enough that a `printf` would do the same job, and then it is a `printf`. Nothing in between lands. An indented heredoc inside a function body depends on whitespace that no reader sees and no diff shows. `<<-` strips leading tabs and nothing else. A reindent converting tabs to spaces leaves the terminator unmatched or the body silently shifted. Neither surfaces as an error at the line that caused it. The two shapes remove the dependency rather than documenting it. This governs what gets written here. A heredoc already in use across the sibling packages is that family's own form, not a defect to go and fix.
- **AWK: always put `;` before a closing `}` when a statement precedes it on the same line** (e.g. `{ f = x; print v > f; close(f); }`, not `close(f) }`). Treat as an axiom, not something to test-and-see. Some non-Linux/non-gawk AWK implementations reject the missing-semicolon form as a hard parse error. It still runs fine on a dev box's `/usr/bin/awk` ("the one true awk"), and passing there proves nothing about the target fleet. Only a statement on its own line immediately before a `}` on its *own* line is safe without a trailing `;`. **The fleet's awk is the floor for every awk program written here, exactly as bash 3.2 is the floor for shell.** The dev box is evidence about neither. The same missing `;` that parses here is a hard error on the servers. The axiom is held by an instrument, not by attention. The owning package's own check pass carries it, and a new or edited awk source goes through that pass before it lands.
- **The axiom is about a statement and a closing brace sharing a line, and a sweep that flags own-line braces produces false positives.** Sweep a whole file rather than a leading portion of it: a partial pass reports a clean tail it never read. Two other things are not awk programs, and are never "fixed" by such a sweep. They are a JSON string literal inside a `printf`, and any brace inside a quoted payload the script only transports.
- **A literal-path search for a creator returns readers only.** A path built in a variable matches no literal-string search, and that is how `mkdir` and friends are normally written. So an absence such a search reports is the expected result, not evidence. Search for the operation and the variable, not the assembled path.
- **Where stdout carries a protocol, every diagnostic goes to stderr, and any emitted string stays one physical line.** On a line-delimited wire a `printf '%s'` of a value holding a newline produces a corrupt frame.
- **A spin loop whose counter resets after each sleep is a pacing counter, not a limit** — unbounded by construction. Read the reset, not the bound.
- **A lock bound defines what happens on expiry**: proceed with the write, or drop that one unit of work. Never exit the process — that turns a single fault into a total outage.
- **A fork placed before a lock stays before it.** Moving it inside the critical section lengthens every hold.
- **A guard script decides from shell builtins alone and fails closed.** Any external binary in the decision path turns that binary's absence into a permit: a JSON parser, a matcher, anything resolved from `PATH`. The call produces empty output and exit 0, which a caller reads as allow. The defect is latent wherever the binary happens to exist, and live everywhere else. So it does not show up on the machine it was written on. Treat unparsed or unexpected input as denial, never as no-objection.
- **`exit` in a sourced include kills the caller's process. A sourced file reports failure with `return`.** Converting one to the other is half a change. A call site that follows the source with an unconditional `return 0` or `shift` swallows the failure, turning a fatal fault into a silent one. Convert the sites and add propagation at every sourcer in the same change.
- **An include that uses `local` and reads `$@` is sourced inside `( set -- <its words> ; . <include> )`, from within a function.** Measured on bash 3.2.57 (Darwin 25.5.0). Sourced that way, the include saw its own `$#` and `$1`, and the caller's `$@` was unchanged afterwards. At the top level the same subshell failed on `local` with `can only be used in a function`, carried on, and left the name empty at rc 0. Bash's own `-n` parse reported nothing for either file, so the defect surfaces only on a run. A pipeline stage is the same subshell, so `producer | ( set -- <words> ; . <include> )` gives the include the producer's stdout as its stdin.
- **`return` semantics, measured on bash 3.2**, three cases, and only the third is a trap:
  - from inside a function it propagates.
  - from the top level of a *sourced* file it propagates as the status of the `.` command.
  - from the top level of an *executed* script it is an error **and execution continues** with status 0. A file with no executable bit that is only ever sourced cannot reach the third case. Verify both of those facts rather than assuming the file is only sourced.
- **A root-level `return` in an include propagates exactly one level**, to the status of the `.` command. That status is not read unless the sourcer tests it. Setting a status is not the same as anyone acting on it.
- **A sourcer that follows the `.` with an unconditional `return 0` discards the sourced file's own verdict.** It is the swallow above, seen from the sourcer's side rather than the include's. It stacks: two such layers between a failing generator and its caller leave the caller's own status check testing a constant. Sourcing inside a pipeline is worse than unconditional, because there the status looks tested and is the wrong one. `$?` after `. file | consumer` is the consumer's, never the sourced file's. On bash, `${PIPESTATUS[0]}` is what carries the generator's.
- **`set +e` before a return escapes to the caller.** That is what makes a cold-start failure survivable where the caller runs `set -e` and calls without `||`. The paired consequence travels with it: a genuine failure later in that same script no longer aborts it. Removing the `set +e` to tidy the return re-breaks cold start unless the call gains `|| :`.
- **awk `NR` is cumulative across input files.** A structural probe keyed on it mis-attributes lines to the wrong file. A brace-depth scan that never tracks closing braces attributes a top-level line to a function it merely sits after. Both give a wrong answer that looks right.
- **Two counts in one output can be two different scopes.** Reading them as one number moving invents a defect that does not exist. Establish each count's scope before comparing them.
- **An ungated line adjacent to a gated guard counts arrivals, not work.** Where the work marker is gated and the gate is off, the honest report is "not observable" — never zero.
- **A nested `bash -c` carries none of the calling shell's functions.** A probe run that way measures the absence of its own harness, not the thing under test.
- **A control that returns the same value as the measurement means the measurement is broken, not that the fix worked.** Run controls both ways: one that must match and one that must not. A check returning 0 whose positive control also returns 0 has established nothing, and is re-measured on the real path rather than reported.
- **HTTP header lines from `curl -D` end in CR LF.** An awk `$2` on the status line is `429\r`, not `429`, so a status comparison never matches. Strip the `\r` (`sub(/\r$/, "", s)`) before comparing any header field.
- **An installer stops only where the services cannot be installed.** Everything configurable later (a missing checkout, key, credential or setting) is a `🙋 WARNING: <where>:` line and the fragment exits 0. A stop is `⛔ ERROR: <where>:`. Both put the emoji first and name the step. A guard names the missing variable. `${VAR:?text}` prints `VAR: text`, so a message convention that needs its marker first uses an explicit test, `[ -n "${V:-}" ] || { echo ... >&2 ; exit 1 ; }`. Under bash `:?` exits 1 and under dash 2.
- **A path variable set together with a mode variable has no second form: a hardcoded path is one of its values with the mode frozen.** Two variables are assigned as a pair, one built literally from the other. A hardcoded spelling equal to one of its values is the same form, not a rival convention. The site then ignores every other mode, silently, and reads as deliberate. Read where each path variable is assigned before judging two spellings as competing forms. Two spellings resolving to the same string under the default mode are indistinguishable at every call site.
- **An unquoted `$( dirname "$0" )` word-splits, and a `;` lets the next command run after the `cd` failed.** The pair produces a wrong but plausible path and exit status 0, so nothing detects it. Quote the substitution and chain with `&&`: the quoted form is correct and returns empty on a failed `cd`. Prefer the form that fails to empty, then guard the empty. Measured on this estate's Darwin box, bash 3.2, and the failure needs a workspace path holding a space, which on Darwin is ordinary.

## Reusable POSIX patterns worth knowing

- **Building a dynamic argv (env vars + binary + args) without `eval`**: POSIX `sh` only gives you one `$@` array. Lean on `env`'s own parsing. It treats each leading argv token matching `identifier=value` as an assignment, stops at the first token that doesn't match, and execs the rest. So `set -- "$@" "NAME=value"` to append pairs. Then append the real binary's *absolute path* and its args: a path starting with `/` can never look like `identifier=value`. Always invoke via `env "$@"`, a harmless no-op prefix when there are zero pairs. No injection risk: each `NAME=value` is one argv token.
- **Portable mutex for a short critical section, no `flock`**: `mkdir` is atomic on every POSIX filesystem and `flock`/`lockf` aren't guaranteed present on bare FreeBSD/Darwin. Take a lock held only microseconds, such as one serializing writes to a shared stdout pipe. A tight-loop `mkdir "$lockDir" 2>/dev/null` retry beats hunting for a portable `flock` equivalent. Add a `sleep 1` fallback after some bound, purely as a deadlock guard. `rmdir` to release. A retry with no ceiling is not a retry but a hang. `mkdir` leaves no owner and no expiry, so a holder that died is a state the loop has to survive: bound the wait, reclaim the directory, and say so on stderr. Unbounded is safe only where the holder cannot die, and inside a backgrounded job it can.
- **A hand-rolled wall-clock timeout with no GNU `timeout(1)`:**
  - background the target directly, not inside a `( ... )` subshell, so `$!` is the real killable PID.
  - run a watcher subshell that polls `kill -0` and does TERM-then-KILL after the deadline.
  - then `wait` on the real PID in the foreground. Known tradeoff: PID-based, not process-group-based, so a grandchild the target forks (e.g. `curl`) isn't guaranteed to die with it.
- **Under `set -m`, `kill -- -$!` on a pipeline reaches the whole job**, although `$!` is the last member's pid, not the group id. Bash maps a job member's pid to its process group, so after the kill no process is left in the group. Only while the leader is still the process that was kept as it was started, though. Once it has ended, the tooling signals what is left one pid at a time. It never signals the group by a number no longer its own (`MAGIC.md`, "`kill` a job's process group, not its pid").
- **The "Terminated: 15" job notice prints when bash reaps the killed job**, which can happen during a later `sleep` rather than at the `wait`. `wait … 2>/dev/null` and `{ wait ; } 2>/dev/null` do not hide it. Wrapping the whole kill-sleep-kill-wait block in `{ … } 2>/dev/null` does.
- **Verify a `%`/`#`/`sed` filename trim against real names before trusting it.** A pattern like `${ITEM%.*}` strips after the last dot. It silently does the wrong thing once a real name contains a literal dot that isn't the suffix. A command listing whose names carry dots is mangled by exactly this. Grep the actual data for the separator character before shipping a trim heuristic.
- **`$$` names the process, not the call, so two writers in one shell collide on a name built from it.** Measured on bash 3.2.57 (Darwin 25.5.0): a subshell and its parent both read the same `$$`, and two separate `bash -c` shells differed, so the value tracks the process alone. `BASHPID` is unset on that floor, so a portable per-subshell identity is not available. A scratch path or generated id built from `$$` is therefore shared between every subshell of one shell, exactly where concurrency is possible. Build the unique part from something the call owns, `mktemp`, rather than from `$$`.

## AWK mechanics that read as something else

- **`RS='\0'` does not slurp a file — it selects paragraph mode.** awk strings are NUL-terminated, so the assigned value collapses to the empty string, and an empty `RS` means paragraph mode. Measured on one-true-awk 20200816: `awk -v RS='\0' 'BEGIN{print length(RS)}'` prints `0`, and a 5-line file containing one blank line yields 2 records rather than 1. Paragraph mode additionally strips trailing newlines and skips leading blank lines. That leading-blank skip silently shifts every byte offset the program reports. A splice driven by those offsets then writes to the wrong place. To read a whole file, rejoin the records under the default `RS` instead.
- **awk cannot see whether its input ended with a newline.** `doc = doc $0 "\n"` reproduces input that ended with one, and adds one that was never there otherwise. `doc = (NR==1) ? $0 : doc "\n" $0` reproduces input that did not end with one, and drops one that did. Neither is correct for both cases, so pick by what the consumer needs and say which one the program implements in its own header.
- **`awk -f prog.awk </dev/null` executes the program. It does not check it.** There is no syntax-only mode. Exit 2 covers a syntax error, a runtime error and the program's own usage guard identically. A sweep keyed on exit status cannot tell them apart, so it reports a working program guarded by a usage check as a failure. Match stderr for `syntax error` instead.
- **`-v` performs backslash decoding on the assigned value. `ENVIRON` does not.** `-v x='C:\path'` loses the backslash before the program ever sees it, which corrupts a path and un-escapes exactly the sequences an earlier escaping stage just produced. Pass any value that can contain a backslash through the environment and read `ENVIRON["NAME"]`. A value holding a newline fails outright, which is the same fix. Measured on one-true-awk 20200816: `-v m="$multi"` exits 2 with `newline in string`, where `M="$multi"` reaches `ENVIRON["M"]` whole at rc 0. The control, `-v` with a one-line value, passes.
- **Calling an undefined function is a fatal exit 2 at call time — one-true-awk and gawk alike.** It is not a warning, and not raised when the program is loaded. A never-taken branch calling a missing function runs clean and exits 0. So no syntax check, dry run or exit-status sweep detects it. What follows for design: an awk library shared through `-f` cannot be layered onto a consumer that may be older than the library. A stale consumer hard-fails on the first call rather than degrading. Where a program has to survive that, carry the shared behaviour in a guarded rule. The rule accumulates input and `next`s past the other rules, with `END` printing. Never carry it in a function the caller must already hold.
- **Pin `LC_ALL=C` for any awk that classifies or emits bytes.** With it pinned, one-true-awk (20200816 and 20250804), mawk 1.3.4 and gawk 5.x agree exactly, and no per-implementation guard is needed:
  - `[[:cntrl:]]` matches 32 characters, `{1–31,127}`.
  - `sprintf("%c", N)` yields one byte for every `N` in 1–255.
  - an `exit N` in `BEGIN` still runs `END` and still exits `N`. Without it they do not agree. gawk 5.3.1 matches 65 characters for `[[:cntrl:]]`. one-true-awk aborts with exit 2 and `towc: multibyte conversion failure` the moment it regex-matches a byte that is not valid UTF-8. The uniformity is a property of the locale, not of the implementations. So the `LC_ALL=C` has to travel with the code, never be assumed from the dev box. NUL is out of reach under every implementation regardless: an awk string cannot hold it, so a byte sweep starts at 1.
- **Don't build shell quoting with `gsub`.** How a `gsub` replacement treats a backslash before a non-special character is undefined across awks, and `'\''` depends on exactly that. Split on `'` and join the parts with `"'\\''"` by plain concatenation, which behaves the same on every awk.
- **A list whose separator is its own statement needs its guard twice, and a guard on one of the two leaves invalid output.** An accumulator built as `if ( acc != "" ) acc = acc ","` then `acc = acc item` has two statements that must be skipped together. Guarding the append alone emits a doubled separator, so a valid input produces output a consumer rejects. Write the append as one statement, `acc = acc ( acc != "" ? "," : "" ) item`, and there is no separator to forget. Measured in awk on this estate's Darwin box, and the original case was a JSON array builder in another package, which was not re-read.
- **A `FS` of one character is literal, and a longer one is a regular expression.** Measured with one-true-awk 20200816 on Darwin. `-F'.'` split `aXb.c` at its dot alone, giving 2 fields, which an ERE dot could not. `-F'|'` split `a|b|c` into 3, where the ERE `|` would split at every character. `-F'::'` split `a::b::c` into 3, so a longer `FS` with no metacharacter is no worse. `-F' | '` on `a | b | c` gave 5, the values `a`, `|`, `b`, `|`, `c`, so it read as the ERE `space or pipe`. `-F'[|]'` and `-F'\|'` each gave 3 on the same subject. Bracket or escape the separator, never leave a metacharacter bare.
- **An annotation written after a free-text field lands on the record's last physical line, not its first.** Measured with one-true-awk 20200816 on Darwin, over records read with `RS='|'`. A `print` carrying an id, a field holding an embedded newline, and a trailing tag emitted two physical lines, and the tag fell to the second. The control, the same text with no newline in the field, stayed on one line. A consumer that classifies by the head line then reads the tag as a continuation and the annotation is lost. Put the annotation first, where the number of physical lines is known.

## Shell constructs that fail quietly

- **A bracket range is collation-dependent, so a range-based whitelist is not a whitelist.** Measured on this estate's Darwin box: `case "A" in [a-z])` matches under `en_US.UTF-8` and does not match under `LC_ALL=C`. Enumerate every accepted character explicitly, or pin `LC_ALL=C` around the test.
- **A glob whose order decides who is served first is decided by collation, and the collation is not always the same.** A walk over `dir/*/` reaches its folders in the order the locale sorts them. Under `LC_ALL=C` uppercase sorts before lowercase, so `slack-C…` comes before `slack-bot-…`. Under `en_US.UTF-8` the order is the other way round. A walk that serves only its first folders therefore starves a different set on each machine, and nothing reports it. Where a glob's order carries meaning, pin `LC_ALL=C` and say in a comment that the order is the contract.
- **A `case` whitelist needs its length and its alphabet written as two separate tests.** Measured on bash 3.2.57 (Darwin 25.5.0) under `en_US.UTF-8`. `?????????*` took nine characters and turned away eight. `*[A-Z]*` matched a lowercase `abcdefghi`, so a bracket range says nothing about which characters are accepted. `*[!ABCDEFGHIJKLMNOPQRSTUVWXYZ]*` then turned away `abcdefghi` and `ABCDEFGH-`, and admitted `ABCDEFGHI`. Arm order carries the rest: a token holding a colon reached the `*:*` arm placed before the bare-id arm, and never reached the bare-id test.
- **A `case` glob states what a value starts with, so a whitelist is written as the complement it must not contain.** Measured on bash 3.2.57 (Darwin 25.5.0). `ABC123*` accepted `ABC123` and `ABC123-x` alike, so the arm admitted a tail it never named. `*[!ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789]*` rejected `ABC123-x` and admitted `ABC123`, which is the question the check was asking. A POSIX ERE answers the same question directly, `^[A-Z0-9]+$`, and is the form to reach for where `grep` is already in the pipeline. Enumerate the accepted characters rather than ranging them, per the bracket-range bullet above.
- **A tool's human-readable output is translated, so matching it is not a test.** `case "$out" in *"Already up to date."*)` suppresses git's no-op message under an English locale, and matches nothing under `es_*` or `ru_*`. The branch inverts, and the quiet path becomes the noisy one on exactly the hosts nobody develops on. Nothing errors, and an English dev box cannot reproduce it. Compare machine-readable state instead: in tooling code, `git rev-parse HEAD` before and after, with `--quiet` on the command. Or read the tool's own `--porcelain`/`--format` output, which is contractually stable. That is code the tooling runs. A member's own git use follows rule on a human's checkout and git identity. `LC_ALL=C` fixes the locale half. It leaves the branch keyed on a message the tool is free to reword between releases, so it is a patch, not the fix. Generalizes to any command whose messages are localized.
- **A trailing `[ … ] && cmd` hands the test's own failure back as the exit status.** Measured: a function ending in `[ 1 = 2 ] && echo yes` returns 1, so a condition that was simply not met reports as a failed function, while `[ 1 = 1 ] || echo no` returns 0. A guard with one consequence is therefore written as the condition that must hold, with `||` carrying the deviation. Examples: `[ -z "$detail" ] || echo "$line" >&2`, `[ "$branch" != "HEAD" ] || branch="main"`. Negate the test where the action belongs on the false side. The `&&` form and an `if … ; then <one statement> ; fi` are the same guard written two other ways, and neither is introduced into a project already writing `||` guards. `set -e` is not the mechanism: it exempts a command inside an `&&`/`||` list. So the failing test does not abort the script, and the exit status is the whole of it.
- **`cmd ; rc=$?` under `set -e` never reaches the assignment** — the shell aborts on `cmd`'s own non-zero status before `$?` is read. `cmd || rc=$?` captures it, because `||` makes the command a tested one.
- **A declaring keyword reports its own status, so `local v="$( cmd )"` never shows `cmd` failing.** Measured on bash 3.2.57 (Darwin 25.5.0): a function ending in `local v="$( false )"` returned 0, where the split pair `local v ; v="$( false )"` returned 1. The control, `local v="$( true )"`, returned 0, so the first 0 is the keyword's and not the substitution's. Under `set -e` the swallowed failure then goes unseen, and the function ran on to its next line at rc 0. `code-craft.md` states the form that avoids it, under "The style".
- **`grep` exits 1 when it finds nothing, and under `set -e` that ends the script at the empty case.** Guard it with `|| :`, never `|| true`: `grep … || :`, `{ grep … || : ; } | …` feeding a pipe, and `( grep … || : )` as a pipeline stage. Count with awk rather than `grep -c`, which also exits 1 at zero: `awk 'BEGIN { c = 0 ; } /pat/ { c++ ; } END { print c ; }'`.
- **A `kill`/`wait` cleanup pair needs `|| :` on each command, because a process already gone is the common case there.** Measured on bash 3.2.57 under `set -e`: `sleep 0 & p=$! ; wait "$p" ; kill "$p" 2>/dev/null` ended at rc 1 without reaching its next line. The same line with `|| :` on the kill reached it at rc 0. The pair usually sits before work owed on the failing run, so the abort skips exactly that work. Guard each command, not only the one that looks risky.
- **A redirection that cannot be opened stops a simple command or a special builtin, and not a compound command.** Measured on bash 3.2.57 (Darwin 25.5.0), with a present file as the control. Under `set -e`, both `: < absent` and `cat -- absent` stop at rc 1. Both `{ cat ; } < absent` and `while … done < absent` print the error and carry on at rc 0. Without `set -e` the special builtin carries on too, so `set -e` is what makes the simple form fatal. Under dash, `:` ends the shell at rc 2, and the braced form still carries on. So guard an optional read at the read itself: `{ … ; } 2>/dev/null < "$f" || :`. That is the only shape measured silent and rc 0 in both shells, on both subjects. Measured on Darwin only.
- **A carve-out suspends `set -e` for a whole function body, so the same function cleans up or does not depending on its call site.** Measured on bash 3.2 and dash: a `cleanUpAfterFailure` whose body runs `false` and then `rm -rf` leaves the directory in place when called plainly. It removes it when the identical call is written `if cleanUpAfterFailure ; then`, `cleanUpAfterFailure || true`, `cleanUpAfterFailure && true`, `! cleanUpAfterFailure` or `while cleanUpAfterFailure ; do`. The suspension covers the entire body, not just the tested command. The function cannot see which call site it got. So cleanup depending on a later line being reached is correct under one caller and broken under the next. A `( … )` subshell's own EXIT trap fires either way. The suspension also reaches a `( … )` subshell on the left of `||`, not a function body alone. Measured on bash 3.2.57: `( set -e ; ( cleanup ) || : ; … )` ran past a `false` inside `cleanup` and continued, where the same subshell called bare ended the shell at rc 1. `trap -p` is not an alternative under `sh`, where dash rejects it outright.
- **The same carve-out defeats the status capture written to catch a failure.** `f || status=$?` is itself one of those call sites, so `set -e` is suspended for the whole of `f`'s body. A failing assignment inside `f` no longer aborts it, and execution runs on to the end. `f` returns its last command's status, 0, so `status` is never assigned and the caller reads success. The idiom that exists to catch the failure is what stops the failure being raised. A status a caller has to see is returned explicitly, from the point that knows it failed. It is never left to fall out of whatever the function happens to run last.
- **Command substitution resets `$?`.** `echo "$(basename "$f"): exit=$?"` reports `basename`'s status, not the status of whatever ran before it. Capture the status into a variable on a line of its own, before any substitution runs.
- **A status read after a pipeline is the last stage's, and the stage that failed goes unreported.** Measured on bash 3.2.57 (Darwin 25.5.0), with the bare command as the control. A function returning 7 reads 7 bare, and 0 through `| tail -1`, `| cat`, or `2>&1 | cat`. Its own status survives in `${PIPESTATUS[*]}`, as `7 0`. Redirect the command on its own and read `$?`, or capture into a variable first. Anything appended for readability, `| tail` and `| head` and `| grep` and `| cat` alike, replaces the status being reported on. A writer killed by a closed pipe shows the same, `yes | head -1` leaving `1 0`.
- **`$1` inside a function is the function's own first argument.** An expression written against the caller's `$1` and later moved into a function silently reads something else. A test site built on it then never exercises what it names. Pass the value in explicitly rather than letting a positional cross a function boundary.
- **Past four operands, `[ … ]` has no specified behaviour, and the shells disagree on where it breaks.** Measured on bash 3.2.57 and dash. Both answered a plain 7-word `-o` test, and both answered 7-word tests whose first operand was `=` or `!=`. Both exited 2 on a 7-word test whose first operand was `!` or `(`, and on the 6-word `-o` forms measured. So the trigger is the shape of the word list, not a fixed set of values. The message is not portable either: bash prints `too many arguments`, dash prints `unexpected operator` or `closing paren expected`. `[ A ] || [ B ]` is two well-specified three-operand tests, and returned 0 or 1 for every value measured, never 2. Write the `||` form wherever `-o` or `-a` would join two tests, rather than judging each value.
- **A failed redirection on a special builtin (`:`, `exec`, `.`) ends a non-interactive POSIX shell**, as on FreeBSD `/bin/sh`. Bash carries on, and macOS `/bin/sh` is bash, so a test there hides it. Test a possibly closed descriptor by writing to it inside `( ... ) 2>/dev/null || fallback`. Bash 3.2 prints the line twice or leaks it to stdout in forms without the subshell.
- **`dash` rejects `==` inside `[` by printing an error *and taking the false branch*.** That is a silently wrong branch in a `#!/bin/sh` script, not a loud failure. `=` is POSIX and behaves identically everywhere, FreeBSD's `/bin/sh` included.
- **`\b` is a GNU extension, and BSD `sed` reads it as a literal `b`, so the pattern matches the wrong lines rather than failing.** The miss and the false hit are both silent. `grep -E '\b'` honours the escape, so a grep result is no evidence about a `sed`. `[[:<:]]` is BSD-only and so no answer across the three platforms. `sed -E` with a captured boundary is the portable replacement, and it keeps the separator: `s/(^|[^[:alnum:]_])hits\[/\1hitTools[/g`. The awk form matches and concatenates by hand, because a `gsub` replacement cannot restore what its own pattern consumed. Measured on this estate's Darwin box only. FreeBSD and Linux were not read for this construct, and the bullet claims nothing about them.
- **`grep -w` treats a hyphen as a word boundary**, so `fgrep -w verbose` matches `very-verbose`. For membership in a space-delimited list use `case " $list " in *" $word "*)`, which compares whole tokens and forks nothing.
- **When the question is whether a line is the same line, the instrument compares whole lines.** `grep -xF` answers an identity question and `grep -F` answers an occurrence question. The two are never substituted for one another. `-x` anchors both ends, and `-F` stops the subject's own punctuation being read as a pattern. Dropping either turns a set comparison into a substring scan. A wrapped fragment of prose then matches for reasons that have nothing to do with copying. A comparison whose result decides whether something is removed carries its control in the same call. Measured on a constructed subject. The tree the reflection was about was not re-read.
- **A function name containing a dot is not a POSIX identifier, and the parse failure takes the whole file.** dash, `/bin/sh` and `bash --posix` refuse to load a file that defines one. Bash and zsh accept it. The parse fails before any line of the file runs, so a compatibility shim inside that same file is impossible. The constraint has to be carried by documentation instead.
- **A `case "$0"` guard in a sourced include reads the caller's `$0`, and its default arm ends the caller.** Measured on bash 3.2.57: an include whose `default` arm ran `exit 1` stopped the script that sourced it at rc 1, and the sourcing script's next line never ran. Run directly, the same file reached its guard's own arm. `$0` holds the sourcing script's name, so a guard written to refuse an unexpected invocation refuses every sourced one. Enumerate the modes that reach the guard before writing a hard exit there, executed-by-path and sourced being two of them.
- **Caller text never lands in a `printf` format string.** A `%` in the data is read as a conversion specifier, so `printf "$msg"` errors or corrupts the output. An unquoted `printf $@` silently drops every word after the first. Always `printf '%s\n' "$msg"`.
- **Command substitution returns when the capture pipe has no writers left, not when the command exits.** `x="$( cmd )"` therefore blocks for as long as *any* process still holds that pipe's write end. A single background child the command leaves behind (`&`, a daemon, `nohup`) hangs the caller for that child's whole lifetime. An `execute` of `sleep 300 & echo STARTED-BG` through such a capture is enough to freeze an MCP server permanently. Every later request goes with it. The same defect is filed publicly against other agent tooling, and documented for ksh93. So it is a property of the construct, not of one implementation. **Never run a caller-supplied or otherwise arbitrary command through `$( )`, process substitution, or a coprocess** — all three wait on pipe EOF. Redirect the command's output to a file, background it directly so `$!` is the real PID, and `wait "$pid"`. Waiting on the process instead of the pipe is immune by construction. Where the caller controls the command text, `( exec >&- ; cmd ) &` is the fix.
  Closing the inherited descriptor, not redirecting it, is what actually
  detaches a lingering grandchild.
- **An unbraced `$var` abutting a non-ASCII character loses the value and eats a byte — under a UTF-8 locale only.** Measured on bash 3.2.57: `v=abc ; printf '%s' "$v──"` emits the five bytes `94 80 e2 94 80`. Bash reads the `─`'s leading `0xE2` as part of the variable name, so `abc\xE2` is an unset variable expanding to nothing. The byte goes with it, leaving a truncated character the terminal renders as a replacement glyph. The braced `"${v}──"` is correct, and under `LC_ALL=C` both forms are correct. So a script that looks right in one locale silently corrupts output in the other, and the dev box may never show it. Brace every expansion that abuts a non-ASCII character. Box-drawing and separator glyphs in progress output are where this actually bites.
- **`mv -f` carries the temp file's mode onto the target**, so a 0644 temp widens a 0600 file it replaces. Create the temp under `( umask 077 && … > "$tmp" )`, or `chmod` the temp — never the target — before the rename. Writing in place with `cat new > target` keeps the inode and therefore the existing mode and ownership, which a temp-plus-rename does not.
- **BSD `seq` counts down when first is greater than last.** `seq 0 -1` prints `0` and `-1` on Darwin, and GNU prints nothing. A `seq 0 $(( n - 1 ))` loop over a possibly empty list therefore runs two bogus iterations on BSD. Guard on `n > 0` before the call.
- **`mv -n` onto a dangling symlink overwrites it.** The no-clobber test follows the link, so a link to a missing target reads as absent: `ln -s 111 a ; ln -s 222 b ; mv -n b a` returns 0 and leaves `a -> 222`. `ln -s` does not follow, and onto an existing dangling `a` it fails with "File exists". Where a name must not be clobbered, a symlink lock included, create it with `ln -s`, never `mv -n`.
